NAME

metadata

DESCRIPTION

Every YAML front matter field in a Markdown post or page is emitted into the generated HTML as a element. The same key-value pair is also written as a data-pagefind-filter attribute on the enclosing

element for PageFind faceted search.

STANDARD FIELDS

Keys are camelCase. The eight marked (BonBon) are the ones Dave Winer’s BonBon reads, so one Markdown file serves both BonBon and the HTML site. Any other key passes through unchanged.

title
(BonBon) Sets in the HTML head (not emitted as <meta> ). Where the text says {{page.title}} it is expanded to this value (see MACROS). </dd> <dt>description</dt> <dd> (BonBon) Short summary for search engines and RSS </dd> <dt>author</dt> <dd> (BonBon) Author name </dd> <dt>pubDate</dt> <dd> (BonBon) Publication date, required for posts. YYYY-MM-DD or an RSS 2.0 date such as Fri, 23 Oct 2026 15:19:45 GMT (see DATES) </dd> <dt>link</dt> <dd> (BonBon) Public URL of the post. Where the title is shown through {{page.title}} it is a link to this address (see MACROS) </dd> <dt>urlPrev</dt> <dd> (BonBon) The previous page. Written as <link rel="prev"> in the head and a Previous link on the page (see PREVIOUS AND NEXT) </dd> <dt>urlNext</dt> <dd> (BonBon) The next page. Written as <link rel="next"> in the head and a Next link on the page (see PREVIOUS AND NEXT) </dd> <dt>rightMarginImage</dt> <dd> (BonBon) An image floated to the right at the top of the text (see MARGIN IMAGE) </dd> <dt>rightMarginImageAlt</dt> <dd> The alt text for rightMarginImage. antenna’s own key, BonBon ignores it </dd> <dt>keywords</dt> <dd> List of tags; each value gets its own <meta> pair </dd> <dt>postPath</dt> <dd> Relative path to the generated HTML file required for posts </dd> <dt>series</dt> <dd> Series name for multi-part posts </dd> <dt>seriesNumber</dt> <dd> Position within the series </dd> <dt>dateCreated</dt> <dd> Creation date </dd> <dt>dateModified</dt> <dd> Last-modified date </dd> <dt>datePublished</dt> <dd> Publication date (alias for pubDate in page context) </dd> </dl> <h1 id="dates">DATES</h1> <p>pubDate may be written as 2026-06-27, as a timestamp such as 2026-06-27T10:00:00Z (quoted or not), or in the RSS 2.0 form BonBon uses, Fri, 23 Oct 2026 15:19:45 GMT. The weekday may be left out, the day may have one or two digits, and the zone may be GMT, UT, a US zone such as EST or PDT, or an offset such as +0200. A date with a zone keeps it: antenna stores “Mon, 30 Nov 2026 21:30:00 -0800” as 2026-11-30T21:30:00-08:00, so the post is on November 30 in the table of contents, the feeds and the page, the day you wrote it, wherever the reader is. A date in GMT, or with no zone, is stored as YYYY-MM-DD HH:MM:SS. Posts sort by the moment they were made. Your Markdown file is never changed. A date antenna cannot read is kept as written and reported with a warning; it does not stop the command.</p> <h1 id="macros">MACROS</h1> <p>In the text of a page or post, {{page.NAME}} is replaced by the front matter value NAME (spaces inside the braces are allowed), so a page can start with a first-level heading that reads {{page.title}}. The value is inserted as plain text: it never becomes Markdown or HTML. Macros are not expanded inside code spans or code blocks, so a page can show one. Expansion is a single pass; a value that itself holds a macro is shown as written. A name the page does not have leaves the macro visible and prints one warning. When the page has a link, the expanded title links to it (http, https, mailto or a relative address). Your published Markdown keeps the macros: BonBon expands them for its readers.</p> <h1 id="previous-and-next">PREVIOUS AND NEXT</h1> <p>urlPrev and urlNext name the previous and next page. A same-site .md address is written as the .html page, like any other link. The page gets <link rel="prev"> and <link rel="next"> in the head and, after its text, a labelled navigation with a Previous and a Next link; only the directions you name are shown. An address that is not http, https, mailto or relative is ignored with a warning.</p> <p>A post that gives neither key gets them when the site is generated, from the site’s table of contents (see antenna help generate): the older post as previous and the newer as next. A page gets none, since the table of contents lists pages in file-name order, which is not a sequence; a page or post in a sequence named in the sequences setting of antenna.yaml gets that sequence’s neighbours instead (see antenna help configuration). A key you write always wins over these.</p> <h1 id="margin-image">MARGIN IMAGE</h1> rightMarginImage is the address of an image (http, https or a relative path). It is shown floated to the right at the top of the text, and on a narrow screen above the text. BonBon’s key has no alt text, so set rightMarginImageAlt to describe the image; without it the image is treated as decoration and has an empty alt. Neither key is also written as a <meta> <p>element.</p> <h1 id="example-front-matter">EXAMPLE FRONT MATTER</h1> <h1 id="controlling-which-fields-are-published-allowed_meta_fields">CONTROLLING WHICH FIELDS ARE PUBLISHED (allowed_meta_fields)</h1> By default all front matter keys are emitted as <meta> <p>elements. To restrict which keys are published, set allowed_meta_fields in page.yaml:</p> <p>allowed_meta_fields: - title - author - description - keywords - series - seriesNumber</p> <p>When this list is set, only the listed keys appear in generated HTML. Internal workflow fields (build flags, notes) are silently omitted.</p> <h1 id="see-also">SEE ALSO</h1> <p>antenna help configuration antenna help post</p> </section> <footer> <p>AntennaApp. This page is also published as <a href="antenna-metadata.7.md">Markdown</a>.</p> </footer> </body> </html>
